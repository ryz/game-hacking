# Commodore 64

Platform notes for `c64` games. The general rules (routes, tokens, the working loop) are in [README.md](README.md).
Added 2026-11-21 and checked with the test disk `tests/make_c64_d64.py` (tests `test_c64_*`). Not tried with a real
game yet: tapes, cartridges, G64 copy protection, fast loaders, multi-disk swaps in a game.

## Backend
VICE x64sc (the cycle-exact C64) as a libretro core, run inside the Python process by `tools/lrcore.py`. Built by
`sh tools/setup_emu.sh c64` (about 21 s) at a pinned commit into `tools/vice/`. True drive emulation (a 1541-II) is
on, warp is off: loads take their real time (the test program: about 5 s of game time).

`tools/vice-debug.patch` makes VICE's savestates exact; a loaded state now continues frame for frame like the
run that saved it, into a new machine or a busy one, before, during and after loading, with keys and joystick in
use (whole machine compared, drive included, 1500 frames). What it fixes, in case a newer core needs it again:
- Saving or loading ran one CPU instruction (the core takes snapshots in a CPU trap): the trap now returns before
  the next opcode. A machine that never ran did its power-on reset after the load: it happens before now.
- The disk drive: its head position was rescaled to the old track and moved again by the restore, its rotation
  state reset (and one field restored from the wrong variable), its CPU re-synchronised, VIA line bits written
  with other masks than read back, and the rotation model switched to the full circuit simulation.
- The CIA time-of-day clocks lost their power-tick counters (and the drive restore re-timed the machine).
- reSID: sound was clocked sample by sample, split by a sub-sample phase that no snapshot holds. The SID is now
  clocked in one piece and makes no audio (the tools never record sound); the cached OSC3/ENV3 values are restored.
- VICE seeds its random generator (drive, CIA, SID, keyboard delays) from the host clock: fixed now.
- State outside VICE's snapshots is kept by the frontend next to each state (`retro_gamedb_hidden_*`): the random
  generator, the drive's speed wobble and rotation model, the keyboard queue (with the history VICE's "release
  older" hack reads), the joystick values, pending keyboard/joystick/typing alarms, autostart's progress.
- The core needs answers for all its options (unset colour options gave a black picture) and asks for the
  audio/video timing: `lrcore.Core(defaults=True, av_info=True)` does what a real frontend does.
- `retro_gamedb_peek/poke/pc`, `insert` (disk into drive 8), `flush` (written tracks to the image file), `busy`.

Speed: about 300-400 frames per second (6-8 times real time).

## A game is a disk, a ZIP of disks, a program, a tape or a cartridge
`python3 tools/intake.py GAME.d64 --region eu|na` (a disk image does not say where it was released). Formats:
`.d64` (the disk name becomes the title and the directory goes into `game.json`), `.g64` (GCR level: copy-protected
originals), `.d71`, `.d81`, `.prg`, `.t64`, `.tap`, `.crt`. A ZIP holding only disk images is a multi-disk game,
disks in name order. Dumps stay in `rom/` (never committed).
- **Power-on is the game started.** The core's autostart types `LOAD"*",8,1` and `RUN` (loads a tape, starts a
  cartridge); the backend runs it on the first frames of a route, keys held at the start are pressed after it.
  Those frames are not counted: a route `w60` is 60 frames after `RUN`. The game's own loading (title picture,
  fast loader) comes after and is shot normally.
- `disk:N` puts disk N into drive 8 (`disk:0` takes it out). There is one drive: `disk2:` is refused. Swap when the
  game asks and give it a moment (`w50`).
- The emulator works on private copies: what the game writes to its disk lands in the copy. `play.py export`
  writes the written images as a ZIP (`.sav`, kept in `rom/saves/`, never committed: whole disk images are game
  data); `sav:NAME` powers on with them.

## Models
`game.json` "model" is `MACHINE[-ntsc][-port1]`, default `c64`:
- `c64` (breadbin, 6581 SID) or `c64c` (8580 SID).
- `ntsc`: a 60 Hz NTSC machine (US releases; some NTSC games run too fast or break on PAL). Default PAL, 50 Hz.
- `port1`: the joystick in port 1 (default port 2, what most games use; some read port 1).

## Screenshots
384x272 (PAL) with the full border, one pixel per C64 pixel; NTSC 384x247. Colodore palette, no blur or CRT
filter, no status bar. The border is part of the picture: many games use it.

## Keys
- Keyboard, by C64 key names: `a`-`z`, `0`-`9`, `return` (also `enter`), `space`, `runstop`, `restore`, `commodore`,
  `ctrl`, `shift`, `rshift`, `shiftlock`, `clrhome` (`home`), `instdel` (`del`), `pound`, `leftarrow`, `uparrow`,
  `plus`, `minus`, `asterisk`, `at`, `colon`, `semicolon`, `equals`, `comma`, `period`, `slash`, `f1`-`f8`, cursor
  keys `up down left right` (up and left are shift + down / right on the real keyboard).
- `type:TEXT` types as written: letters as plain keys (capitals in the power-on mode), C64 symbol layout with
  shift where needed (`"` is shift+2, `(` shift+8, `[` shift+colon). `runstop+restore` is the warm reset.
- Joystick: `joyup joydown joyleft joyright fire` (`fire+joyright:30`).
- `w30` is "wait 30 frames" (`w` is the W key on its own).

## Memory
- `0000`-`FFFF`: what the CPU sees now (BASIC/KERNAL/character ROM and I/O as banked; I/O read without side
  effects). `poke` there is a CPU write: RAM, the RAM under a ROM, or an I/O register (`poke:D020=00` sets the border).
- `10000`-`1FFFF`: the 64K RAM as stored, whatever is banked over it (games keep data under the ROMs and I/O).
- `find`/`dump` search the RAM as stored, at CPU addresses. `status` shows the program counter.
- `play.py text` reads the 40x25 text screen where the VIC-II reads it (screen codes, upper case/graphics or
  lower case set); meaningless on bitmap screens.
